# `column.width_*` — wrongly recorded as inert

**Status: resolved — wiki corrected 2026-07-29.** Kept as the record of a wrong claim and how the
real mechanism works.

## The wrong claim

[[recipes/service-card-grid]] ("Gotcha: inert props survive an export") listed `column.width_medium`
as *"Pre-5.0 leftover — column widths now live in the parent row's layout string"*. The inference
came from `width_medium` not being declared in `column/element.php`'s own `fields`.

## What the demos showed

The official demos in [[sources/websites-demo]] carry `width_medium` on 549 columns and
`width_small` on 221 — always alongside a `row.layout` string. YOOtheme's own authors do not
serialise a dead prop 770 times.

## The actual mechanism, verified in the source

- **The column template renders the widths directly** —
  `column/templates/template.php:45-51`: `uk-width-{width_default}`, `uk-width-{width_small}@s`,
  `…@m`, `…@l`, `…@xl`, with `uk-width-1-1` as fallback when none is set
- **The row edits them** — the *Column Layout* panel in `row/element.php:367-` declares
  `width_default/small/medium/large/xlarge` as `'type' => 'child-prop'` fields: edited in the row
  UI, **stored on the child column nodes**. That is why `column/element.php` does not declare them
- **`row.layout` is the authoring shorthand** — the Layout select's preset values
  (`1-2,1-2`, `1-4,1-4,1-4,1-4|1-2,1-2,1-2,1-2`, …) and, on import of old layouts, the
  `2.1.0-beta.1.1` migration in `row/updates.php:84-169` expands the string into per-child
  `width_{breakpoint}` props (the `|` separator feeds the next-smaller breakpoint tier). The
  migration does **not** remove `row.layout`, which is why exports carry both

So: `row.layout` records the chosen preset; `column.width_*` are the rendered truth; a hand-written
snippet may use either (`row.layout` is expanded on import), but reading an export means reading
the column props.

## What was corrected

- [[recipes/service-card-grid]] — the `column.width_medium` row of the inert-props table now
  carries the correction; the other two rows of that table (`column.text_align`,
  `gallery.panel_image_no_padding`) remain valid
- [[sources/websites-demo]] — records the finding under "Recurring techniques"

## Still open

Nothing for this issue. The production layout that triggered the original claim
([[sources/production-layout-sample]]) carried `width_medium` on 4 columns — those were real,
functioning widths, not leftovers.

## Confirmed real-world case (2026-09-08)

A hand-authored `chi-siamo.json` (root `"version": "5.0.43"`) set only `row.props.layout:
"1-2,1-2"` on its "Storia" row, with no `width_*` on either column. Opened in the builder, that
1/2 grid rendered as two full-width stacked columns instead of side-by-side — fixed only by
manually reselecting the 1/2 fraction in the row's *Column Layout* panel. Comparing the file before
and after that manual fix: the only functional change on the row is both columns gaining
`"width_medium": "1-2"` — confirming this page's mechanism end-to-end, this time from the missing
side rather than the demo-confirmed side. Every other row in the same file uses `layout: ""`
(single full-width column) and never needed `width_*`, which is why only the one fraction row
broke.

Root cause, pinned to the exact lines: `column/templates/template.php:45` emits `uk-width-1-1` only
when none of `width_default/small/medium/large/xlarge` is set on the column — that fallback is what
produced the stacked columns. The migration that would normally derive `width_*` from `row.layout`
on import, `row/updates.php:90-169` (keyed `2.1.0-beta.0.1`), is version-gated: it only runs for
nodes whose declared version predates that key. A file that already declares a recent `version`
(here `5.0.43`, same as the installed theme) causes the builder to skip it, on the assumption the
data is already in post-migration shape. So `row.layout` alone is only safe input for an *old*
`version` stamp; any file authored with a current `version` — which includes every layout this repo
generates — must carry the matching `width_*` on each column explicitly. Captured in
`raw/observations/2026-09-08-storia-grid-width-medium-reselect.md`; propagated to
[[concepts/ai-layout-generation]] and to the `json-schema` skill (`SKILL.md` v2.6.0,
`references/schema-spec.md`).

## Second confirmed case (2026-10-01) — and why the rule did not stick

Seven client service-page layouts generated by `/yootheme-wiki` repeated the bug on every
`1-2,1-2` row; the user's corrected export differs only by `"width_medium": "1-2"` on each column
(`raw/observations/2026-10-01-servizi-grid-width-medium.md`). The fix of 2026-09-08 had reached the
`json-schema` SKILL.md but not the two places the agent actually consults while generating:
the root `SKILL.md` (invariants, common mistakes, mechanical check) and the `column` entry of
`references/element-types.md`, which still described width as coming from the row. Both corrected
with the user's approval: root `SKILL.md` gains the invariant, a common-mistake row, a red flag and a
`jq` check (fractional row with a column lacking `width_medium` → must be `[]`); `element-types.md`
lists `width_*` on `column`, shows them in the `row` and `column` examples; skill bumped to v2.7.0.
